# Privacy

What this resolver retains, what it does not, and what is outside its control.
Every claim here corresponds to a specific setting in this repository, and
`make audit` checks the running server against them. If the audit fails, this
document is wrong about that node — trust the audit, not the prose.

## Nothing about your queries is written to disk on this server

Not sampled, not aggregated, not rotated. There is no query log to turn off,
misplace, or hand over, because none is ever created.

That claim is about *this server*, and the heading says so deliberately. Queries
are forwarded to an upstream resolver, which receives every name looked up and has
its own retention policy. See "What this cannot promise" below — it is the first
item there, not a footnote.

| Component | Setting | Where |
|---|---|---|
| unbound | `log-queries: no`, `log-replies: no`, `log-local-actions: no`, `log-servfail: no` | `node/unbound/unbound.conf.tmpl` |
| unbound | `verbosity: 0`, `use-syslog: no`, `logfile: ""` | same |
| unbound | `statistics-interval: 0`, `extended-statistics: no` | same |
| unbound | `module-config` omits `subnetcache`, so EDNS Client Subnet is never attached | same |
| unbound | queries are forwarded only over authenticated DNS-over-TLS, never in cleartext; `forward-first: no` so an unreachable upstream fails rather than silently recursing | asserted at runtime by `make audit` |
| unbound | `rpz-log: no` on every policy zone | generated by `node/bootstrap.sh` |
| dnsdist | no `LogAction`, `RemoteLogAction`, `carbonServer`, dnstap or frame-stream logger anywhere | `node/dnsdist/dnsdist.conf.tmpl` |
| journald | `Storage=volatile` — the journal is a ramdisk and does not survive reboot | `node/systemd/journald-privacy.conf` |
| journald | `/var/log/journal` is removed; `rsyslog` is purged if present | `node/bootstrap.sh` |
| nftables | not one `log` statement in the ruleset | `node/nftables/nftables.conf.tmpl` |
| — | no reverse proxy and no HTTP server, so no access log exists | port 80 is never opened |

`make audit` does not take the configuration's word for it. It sends a query with
a randomly generated name, waits, and then searches `/var`, `/etc`, `/root`,
`/home`, `/tmp`, `/srv` and `/opt` for that name. A config review proves the
config is right; that search is what would catch a component logging somewhere
nobody thought to look.

## What exists in memory, and for how long

Being straight about this matters more than a clean-sounding absolute. A resolver
that knew nothing at all could not answer a query or stop an attack.

| Data | Where | Lifetime |
|---|---|---|
| Recent query names and client IPs | dnsdist ring buffer, 5,000 entries by default | Overwritten continuously — seconds at any real traffic level. Never written to disk. Needed for dynamic blocking. |
| Client IPs currently rate-limited | dnsdist dynamic block table | The block duration, 60s by default |
| Per-IP query counters | dnsdist `MaxQPSIPRule` | A sliding one-second window |
| Query names and answers | unbound's DNS cache | The record's TTL. **Not associated with any client** — the cache cannot say who asked. |
| Client IPs of open connections | Linux conntrack and socket tables | The life of the connection. Unavoidable in any networked service. |
| Warnings and errors | journald, in RAM | Until reboot, capped at 16 MB. `MaxLevelStore=warning`, so routine operation logs nothing. |

Responses are not recorded in the ring at all (`recordResponses = false`), so
what was *answered* is never retained even transiently.

Set `dynblock_ring_entries = 0` in `terraform.tfvars` and the ring disappears
entirely: no query name or client IP exists anywhere in the system, at any point.
The cost is that dynamic blocking stops working, leaving only the per-IP rate
ceiling, so a sustained flood is throttled but never blocked outright.

## What is written to disk

A privacy document that claims a clean sheet is not credible. These files exist:

- **`/var/log/letsencrypt/`** — certbot's own logs. ACME protocol exchanges with
  Let's Encrypt about the server's certificate. No client data of any kind.
- **`/var/log/unattended-upgrades/`** — package names and versions installed.
- **`/var/lib/unbound/rpz/*.rpz`** — the blocklists themselves. These are lists we
  downloaded, not records of anything anyone asked for.
- **`/etc/letsencrypt/aws.credentials`** — the Route 53 IAM key, mode 0600.

`make audit` reports each of these explicitly rather than staying quiet about them.

## What blocking does to your queries

Blocking happens in two places, and you should know which is which, because they
differ in who decides and in whether it can be overridden.

**On this server**, as RPZ, in this order, first match wins:

1. **Allowlist** (`node/unbound/rpz/allowlist.rpz`) — local, version-controlled,
   evaluated first so it overrides everything below it. Ships empty: nothing is
   exempt from filtering unless you add it.
2. **Ads and trackers** — Hagezi Pro, ~456,000 domains.
3. **Malicious response IPs** — Hagezi TIF IPs, ~72,000 entries, blocking
   resolution *to* known-bad addresses whatever domain was asked for. Kept locally
   because no domain-reputation feed can do this: it catches a brand-new or
   compromised domain pointing at known command-and-control infrastructure.

These lists are in this repository. You can read exactly what is blocked and why,
and the allowlist is the final word.

**At the upstream resolver**, currently Quad9's filtered endpoint
(`dns.quad9.net`): malware, phishing and command-and-control domains, from
commercial threat intelligence updated continuously. This replaced a
1,747,000-entry local feed, which was both staler and the single largest claim on
this node's memory.

Be clear about what that trade costs you:

- **That policy is not ours and we cannot show it to you.** Quad9 decides what is
  blocked. There is no list in this repository to read.
- **The allowlist cannot override it.** An upstream NXDOMAIN arrives as an answer;
  it never reaches response-policy processing, so `rpz-passthru` is powerless
  against it. The remedy is a per-domain forward to Quad9's unfiltered endpoint,
  documented in the README under "Overriding an upstream block" — which is a
  manual operator action, not something the allowlist does for you.
- **Set `forward_tls_upstreams = []`** and all of this reverts to full recursion
  with no third party, at the cost of losing malware blocking until you add a feed
  back to `rpz_blocklists`.

Two further consequences, which apply to blocking wherever it happens:

- **A blocked name returns NXDOMAIN, and that answer is not DNSSEC-signed.** If
  your client validates DNSSEC itself, a blocked lookup looks like an unsigned
  denial rather than a cryptographically proven one. This is inherent to RPZ
  filtering and is not specific to this resolver.
- **Threat feeds have false positives**, and response-IP blocking has the most —
  one shared CDN address in the feed can take out every site behind it. The
  allowlist is the remedy and the README documents both the domain and the
  reversed-octet IP syntax.

## What this cannot promise

- **The upstream resolver sees every query name.** This is the central trade in
  the design, so it comes first. Queries leave this server over authenticated
  DNS-over-TLS to Quad9 (`dns.quad9.net`), which therefore receives every name
  this resolver looks up. What Quad9 does *not* receive is any client: every query
  arrives from this node's single IP address, so your address is never disclosed to
  them and this server acts as a mixer for everyone using it. Quad9 is a Swiss
  non-profit with a published no-logging policy and third-party audits. We cannot
  verify that policy, and neither can you — it is trust, one hop further out.

  Why accept a third party at all, when full recursion needs none? Because
  recursion speaks **cleartext DNS on port 53**. Resolving from the root means
  every query name crosses the hosting provider's network in the clear, and the
  provider *also* sees every client IP arriving on 443 and 853. That puts both
  halves of the identifying pair in one company's hands. Forwarding over TLS splits
  them: the provider keeps client IPs and sees only ciphertext leaving, the
  upstream sees names and never sees a client, and neither can reconstruct who
  asked what without the other's cooperation.

  `forward_tls_upstreams = []` reverts to full recursion if you would rather make
  the opposite trade. `make audit` asserts whichever posture is configured.

- **`qname-minimisation` is worth less than it sounds.** It is enabled, and it does
  limit what each individual nameserver in a recursion chain learns. It does almost
  nothing against a network observer, who sees every step of the chain and
  reassembles the full name from the parts. While forwarding it is close to moot,
  since the whole name goes to the upstream in one query. It is not a defence
  against anyone watching the wire.

- **Hetzner can see your traffic metadata.** They operate the network and the
  hypervisor. They see every client IP that connects, with timing and volume — the
  very data this resolver refuses to retain — and the TLS SNI, which names the
  resolver. They do not see query names, because upstream traffic is encrypted.
  They can image the running VM, memory included, which would expose the dnsdist
  ring buffer, unbound's cache, and the TLS private key. No configuration inside
  the VM changes any of this. If your threat model includes the hosting provider,
  this resolver is not the answer.

- **A resolver with few users protects them less.** Correlating a client to a query
  requires matching inbound connections against outbound traffic. With many
  concurrent users, queries interleave and that gets hard. With one user, anything
  leaving is obviously theirs. This is a property of traffic volume, not of
  configuration, and no setting in this repository improves it.

- **The hostname is public.** Every Let's Encrypt certificate is published to
  Certificate Transparency logs, so the resolver's name is permanently and
  publicly discoverable. That is a property of the trusted-certificate system,
  not a leak.

- **The forwarding posture failed silently once, which is why it is now asserted
  behaviourally.** Debian's `unbound-resolvconf.service` takes the nameservers the
  network hands out over DHCP and installs them into unbound as a root forward zone
  **at runtime**, through `unbound-control`. It appears in no configuration file.
  For a period after the first deploy this resolver was forwarding every query name
  in cleartext to the hosting provider's resolvers while every config file said it
  was recursing, and while `make audit` reported no failures.

  It was found by asking an authoritative server which address it saw. That is now
  an audit check. `make audit` asserts that the running forward zone matches the
  configured upstreams, that the transport is TLS, that every upstream carries a
  `#tls-auth-name` so the certificate is actually verified, that `forward-first` is
  `no` so an unreachable upstream cannot cause a silent fallback to cleartext, that
  `unbound-resolvconf` is masked, and — behaviourally — that an authoritative
  server does *not* report this node's own address. A config that merely looks
  right no longer satisfies it.
- **AWS Route 53 holds the DNS zone** for the resolver's hostname, because ACME
  DNS-01 validation is done there, and Terraform manages the resolver's A/AAAA
  records in the same zone. AWS therefore sees the zone's contents and the
  short-lived `_acme-challenge` TXT records, but no client query ever reaches it.
- **Legal compulsion.** Server operators can be ordered to start logging. What
  this design gives you is that there is nothing retained to hand over about the
  past. It cannot promise anything about the future.
- **Timing and volume are observable** to anyone watching the network, even though
  the content is encrypted.
- **This is one operator's server.** You are trusting whoever runs it. The
  verifiable part is that the configuration is in this repository and
  `make audit` checks the running system against it.

## Verifying for yourself

```sh
make audit    # on the server: asserts every claim above, exits nonzero on failure
make test     # from your machine: transports, DNSSEC, blocking, port 53 closed
```

`make audit` prints PASS, WARN or FAIL per check and fails the run on any FAIL.
